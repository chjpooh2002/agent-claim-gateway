# CS 에이전트 주문 처리 연동 계층 — 프로젝트 기획서

Nov 6, 2026 · @홍준

## 1. 프로젝트 개요와 목적

서로 다른 방식의 API를 가진 가짜 쇼핑몰 2개를 하나의 취소·반품 인터페이스로 묶고, AI 에이전트가 이를 안전하게 호출하도록 만드는 파이썬 백엔드를 만든다.

- **목적 1 — 지원 포트폴리오**: 제너러티브랩 현장실습 "백엔드 엔지니어 – AI 에이전트 시스템 연동" 직무 지원용. 실습 내용인 "국내외 약 50개 커머스·물류 시스템 연동"을 2개 몰 규모로 축소 재현한다.
- **목적 2 — 판단력 훈련**: 코드 작성보다 설계 판단에 무게를 둔다. 판단 지점마다 직접 결정하고, 그 근거를 기록으로 남긴다.
- **목적 3 — 면접 대비**: 모든 결정이 예상 면접 질문 하나에 대응하도록 설계한다.

핵심 메시지: "에이전트가 실제 업무를 처리하게 만들 때 어려운 건 모델이 아니라, 제각각인 외부 시스템을 믿을 수 있게 다루는 일이다."

## 2. 진행 방식과 역할 분담

홍준은 판단하고 리뷰하며, 멘토(Claude)는 판단 지점을 제시하고 결정된 내용을 코드로 옮긴다.

| 역할 | 맡는 일 |
| --- | --- |
| 홍준 | 설계 결정, 결정 기록 작성, 모든 코드 리뷰와 병합 판단, 문서·발표 |
| 멘토 | 판단 지점과 선택지 제시, 결정에 대한 반박, 관련 개념 설명, 코드 작성 |

**한 판단 지점의 진행 순서**

1. 멘토가 질문을 던진다 (선택지는 바로 주지 않음).
2. 홍준이 먼저 자기 답과 근거를 쓴다.
3. 멘토가 반박하거나 놓친 경우를 짚는다.
4. 결정을 기록한다.
5. 멘토가 코드를 작성하고, 홍준이 리뷰한 뒤 병합한다.

**결정 기록 형식** (저장소 `docs/결정기록/`에 한 결정당 한 파일)

- 맥락: 무엇을 정해야 했나
- 선택지: 검토한 안 2\~3개
- 결정과 근거
- 버린 안과 버린 이유
- 결정을 뒤집을 조건

**작업 규칙** (상세는 저장소 `CONTRIBUTING.md`)

- 이슈: 판단 지점 하나, 기능 하나당 이슈 하나. 결정 기록과 서로 링크한다.
- 브랜치: `main`은 직접 커밋 금지. 작업은 `feat/12-outbox-worker`처럼 종류/이슈번호-설명.
- PR: AI가 작성한 코드는 반드시 PR로 들어온다. CI 통과 + 홍준의 리뷰 체크리스트(줄 단위로 설명 가능한가) 통과 후 스쿼시 병합.
- 커밋: 컨벤셔널 커밋 형식 (`feat:`, `fix:`, `test:`, `docs:` 등), 제목은 한국어.

**위험 요소 — 솔직하게**

- **코드를 전혀 안 쓰면 면접에서 무너진다.** 공고는 "파이썬으로 프로그램을 만들어 본 경험"을 요구하고, 면접관은 코드 한 줄을 짚어 물어볼 수 있다. 대응: 홍준이 줄 단위로 설명할 수 없는 코드는 병합하지 않는다. 그리고 최소 한 부분(쇼핑몰 B 어댑터 또는 정책 계층 테스트)은 직접 작성한다.
- **AI 도구 사용은 숨기지 않는다.** 저장소 설명에 "설계 결정은 직접, 구현은 AI 코딩 도구와 협업"이라고 밝힌다. AI 에이전트 회사라 오히려 협업 방식을 설명할 수 있는 게 강점이 된다. 숨겼다가 드러나면 치명적이다.
- **판단 지점이 많아 일정이 밀릴 수 있다.** 결정 하나에 하루 이상 쓰지 않는다. 막히면 멘토 추천안으로 가고, 결정 기록에 "보류한 고민"으로 남긴다.

## 3. 요구 역량 대응표

공고의 필수·우대 항목과 실습 업무 하나하나에 이 프로젝트의 증거가 하나 이상 대응하도록 설계했다.

| 공고 항목 | 구분 | 프로젝트에서의 증거 |
| --- | --- | --- |
| 파이썬 또는 자바스크립트로 프로그램 제작 경험 | 필수 | 파이썬(FastAPI) 백엔드 전체, 직접 작성한 어댑터 1개 |
| API·데이터베이스 기본 개념 | 필수 | 공통 주문 처리 API 설계, 클레임·멱등 키·아웃박스 테이블 |
| 낯선 시스템과 문서를 끝까지 파고드는 끈기 | 필수 | 몰별 API 명세 정리 문서, 트러블슈팅 기록 2\~3건 |
| 스스로 조사하고 질문하며 해결하는 태도 | 필수 | 결정 기록 (선택지·근거·버린 안·관련 CS 지식) |
| Git 사용 경험 | 우대 | 기능 단위 브랜치와 PR, 리뷰 흔적 |
| 개인·팀 개발 프로젝트 경험 | 우대 | 본 프로젝트 + 기존 팀 프로젝트들 |
| 외부 API 연동 경험 | 우대 | 어댑터 계층, 모델 호출도 외부 시스템처럼 시간 초과·재시도 적용 |
| 클라우드 환경 사용 경험 | 우대 | 기존 프로젝트로 답변. 본 프로젝트는 도커 컴포즈 실행, 배포는 시간 남을 때 |
| 실습 업무: 테스트 자동화 | 업무 | CI에서 도는 장애 주입 테스트 |
| 실습 업무: 실서비스 이슈 대응 | 업무 | 추적 로그 + 운영 지표로 "취소가 안 됐다" 문의를 좁혀가는 시연 |
| 실습 업무: 코드 리뷰를 받으며 협업 | 업무 | PR 단위 작업, 리뷰 코멘트 반영 기록 |

추가로 다른 백엔드 공고에서 공통으로 보는 성능 측정·개선, 메시지 기반 처리, 배포 후 지표 관리를 각각 부하 테스트, 아웃박스, 운영 지표로 작게 경험한다.

## 4. 범위

몰 2개를 깊게 연동하고, 에이전트는 얇게 붙인다. 화면은 만들지 않는다. 교환과 배포를 뺀 시간은 성능 측정, 아웃박스, 운영 지표에 쓴다.

**만드는 것**

- 가짜 쇼핑몰 서버 2개 (몰 A, 몰 B — 의도적으로 다른 설계)
- 공통 주문·클레임 모델과 몰별 어댑터 (취소·반품)
- 업무 정책 계층 (취소·반품 가능 여부 판단)
- 멱등성, 시간 초과, 재시도, 결과 불확실 시 재조회
- 아웃박스 패턴: 처리할 외부 호출을 같은 트랜잭션으로 DB에 먼저 기록하고, 별도 작업자가 꺼내 수행
- 에이전트 도구 호출 연결 (얇게) + 되돌릴 수 없는 작업 전 고객 확인 단계 + 상담원 이관
- 추적 로그와 운영 지표 (몰별 성공률·재시도율·이관률·외부 호출 지연)
- 부하 테스트로 처리량·응답 시간 측정, 병목 하나를 고친 전후 수치 기록
- 자동화 테스트와 CI, 도커 컴포즈로 전체를 한 번에 실행

**만들지 않는 것**

- 교환 (반품 + 재배송이 엮여 상태 설계가 두 배. 넣는다면 어떻게 설계할지만 결정 기록으로 남김)
- 메시지 브로커(Kafka) 실제 도입 (아웃박스로 개념만 구현, 몰이 늘 때 교체할 지점은 문서로)
- 채팅 화면이나 관리자 화면 (터미널 대화 또는 API 호출 예시로 대체)
- 문서 검색 기반 답변, 여러 에이전트 협업
- 실제 결제·환불 처리 (몰이 환불했다고 응답하는 데까지만)
- 회원 인증·권한 체계 (고객 식별값은 요청에 포함된다고 가정)

**시간이 남으면**

- 클라우드 배포와 인프라 코드화 (측정과 지표는 로컬 실행으로 충분하므로 마지막 순위)

## 5. 시스템 구성

몰마다 다른 점은 어댑터 안에서만 처리하고, 그 위 계층들은 몰이 몇 개든 같은 코드로 동작한다.

&#91;embedded content: 시스템 구성 · 계층 4개, 몰 2개\]

강조한 연동 계층이 이 프로젝트의 중심이다. 몰이 늘어나면 어댑터만 추가된다.

**취소 요청 하나의 흐름**

1. 에이전트가 고객 대화에서 주문번호와 대상 상품을 파악해 취소 도구를 호출한다.
2. 주문 처리 API가 멱등 키를 확인한다. 이미 처리된 요청이면 저장된 결과를 바로 돌려준다.
3. 정책 계층이 현재 배송 상태로 취소 가능 여부를 판단한다. 불가하면 반품 안내 같은 대안을 돌려준다.
4. 가능하면 에이전트에게 고객 확인을 요청하고, 확인을 받은 뒤 진행한다.
5. 클레임과 "몰에 취소 요청할 일"을 같은 트랜잭션으로 DB에 기록한다 (아웃박스).
6. 아웃박스 작업자가 기록을 꺼내 연동 계층을 통해 해당 몰의 어댑터로 요청한다. 실패·시간 초과 시 9절 원칙대로 처리한다.
7. 결과를 저장하고 지표를 남긴다. 에이전트는 클레임 상태를 조회해 고객에게 결과를 안내한다.

**기술 스택**

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 언어·프레임워크 | 파이썬 3.12, FastAPI | 공고 요구 언어, 비동기 처리 지원 |
| 패키지 관리 | uv | 설치가 빠르고 잠금 파일로 재현 가능 |
| DB | MySQL 8 | 이미 익숙한 DB라 학습 부담을 줄임. 잠긴 행 건너뛰기를 지원해 아웃박스 작업자 구현 가능 |
| DB 접근 | SQLAlchemy 2 | 동기·비동기 방식은 판단 지점 4에서 결정 |
| 테스트·품질 | pytest, ruff | 파이썬 표준에 가까운 조합 |
| 실행·CI | 도커 컴포즈, 깃허브 액션 | 한 명령으로 전체 실행, PR마다 자동 검사 |
| 부하 테스트·지표 | 미정 | 판단 지점 9에서 결정 |

## 6. 도메인 모델 초안

상태는 "배송 상태"와 "클레임 상태" 두 축으로 나누고, 주문이 아닌 주문 항목 단위로 둔다.

- **두 축 분리 이유**: 상태 하나에 "배송중", "취소요청", "반품완료"를 다 넣으면 "배송완료 상태에서 교환 진행 중" 같은 조합을 표현할 수 없다.
- **항목 단위 이유**: 셔츠 2장 중 1장만 반품하는 부분 클레임이 일상이다. 주문 전체 상태는 저장하지 않고 항목들로부터 계산한다.

| 엔티티 | 주요 필드 | 설계 근거 |
| --- | --- | --- |
| 주문 | 몰코드, 외부주문번호, 주문일시(시간대 포함), 고객식별값, 원본응답 | 몰코드 + 외부주문번호가 유일 키. 원본응답은 변환 버그 디버깅용으로 그대로 보관 |
| 주문항목 | 외부항목번호, 상품명, 옵션, 수량, 결제금액(원 단위 정수), 배송상태, 배송완료일시 | 금액은 부동소수 오차를 피해 정수. 배송완료일시는 반품 기한 계산 기준 |
| 클레임 | 클레임번호, 멱등키, 유형, 대상(항목·수량), 사유, 상태, 외부클레임번호, 실패사유 | 한 항목에 클레임이 여러 번 생길 수 있어 독립 기록으로 둠 |

**상태 값**

- 배송 상태: 결제완료 · 상품준비중 · 배송중 · 배송완료 · 구매확정 · 알수없음
- 클레임 유형: 취소 · 반품 (교환은 범위 밖)
- 클레임 상태: 접수됨 · 외부처리중 · 완료 · 거절됨 · 실패 · 상담원이관

**변환 원칙**: 몰이 준 상태값이 변환표에 없으면 추측하지 않고 "알수없음"으로 보낸 뒤 경고 로그를 남긴다. 잘못 매핑하면 에이전트가 반품 불가 상품을 반품 처리할 수 있다.

**열린 질문**

- [ ] 교환을 넣는다면 클레임 하나로 볼지, "반품 + 재배송" 두 흐름으로 쪼갤지 (구현 없이 결정 기록만)
- [ ] 주문 정보를 우리 DB에 저장할지, 매번 몰에서 조회할지 (캐시 정합성 문제)

## 7. 업무 정책과 상태 전이

요청 가능 여부는 배송 상태 하나로 결정되고, 불가한 요청은 거절이 아니라 가능한 대안으로 안내한다.

| 배송 상태 | 취소 | 반품 |
| --- | --- | --- |
| 결제완료 | 즉시 처리 | 불가 → 취소로 안내 |
| 상품준비중 | 몰에 취소 요청 (판매자 승인 필요할 수 있음) | 불가 → 취소로 안내 |
| 배송중 | 불가 → 반품으로 안내 | 수령 후 접수 안내 |
| 배송완료 | 불가 → 반품으로 안내 | 기한(7일) 내면 접수 |
| 구매확정 | 불가 | 불가 → 상담원 이관 |
| 알수없음 | 상담원 이관 | 상담원 이관 |

기한 7일은 가정값이다. 몰마다 다를 수 있어, 몰별 설정으로 뺄지는 판단 지점으로 남긴다.

## 8. 가짜 쇼핑몰 설계

두 몰은 연동 계층이 흡수해야 할 차이를 일부러 최대한 다르게 만든다. 이 차이가 어댑터 설계를 검증하는 시험지다.

| 항목 | 몰 A | 몰 B |
| --- | --- | --- |
| 인증 | 토큰 발급 후 만료 (만료 시 재발급 필요) | 고정 키를 요청 머리글에 포함 |
| 상태 표현 | 숫자 코드 (예: 10, 20, 30) | 영문 문자열 코드 |
| 목록 조회 | 쪽 번호 방식 | 커서 방식 |
| 취소 처리 | 즉시 결과 응답 (동기) | 접수만 받고 결과는 나중에 조회 (비동기) |
| 오류 응답 | 상태 코드 + 오류 코드 필드 | 항상 200 응답 + 본문에 성공 여부 |
| 시간 표기 | 한국 시간, 시간대 표기 없음 | 세계 표준시, 시간대 표기 포함 |
| 장애 주입 | 설정으로 지연·500 오류 확률 조절 | 동일 + 같은 요청 중복 시 중복 처리되는 결함 |

- **몰 B의 "항상 200"**: 실제 외부 시스템에서 흔하다. 상태 코드만 보고 성공 판단하면 실패를 성공으로 처리하는 버그가 난다.
- **몰 B의 중복 처리 결함**: 외부 시스템이 멱등성을 보장하지 않을 때 우리 쪽에서 막아야 한다는 걸 보여주는 장치다.
- **시간 표기 차이**: 반품 기한(배송완료 후 7일) 계산이 시간대 때문에 하루 틀어지는 버그를 재현할 수 있다.

## 9. 장애 시나리오와 대응 원칙

대원칙: 결과를 모르면 추측하지 않고, 확인한 뒤 움직인다. 확인도 안 되면 사람에게 넘긴다.

| 시나리오 | 위험 | 대응 원칙 |
| --- | --- | --- |
| 에이전트가 같은 취소를 두 번 요청 | 이중 취소, 이중 환불 | 멱등 키로 첫 결과를 저장하고 두 번째는 저장된 결과 반환 |
| 취소 요청이 시간 초과 | 몰에서 처리됐는지 모름 | 바로 재시도하지 않고 몰의 현재 상태를 재조회한 뒤 결정 |
| 몰이 500 오류 | 일시 장애인지 영구 실패인지 모름 | 정해진 횟수만 간격을 늘려가며 재시도, 초과 시 상담원 이관 |
| 몰이 4xx 오류 (잘못된 요청, 권한 없음) | 재시도해도 같은 결과 | 재시도하지 않고 오류 유형 분류 후 안내 또는 이관 |
| 서버가 외부 호출 직전·직후에 죽음 | 요청이 사라지거나 기록과 실제가 불일치 | 아웃박스에 남은 작업을 재시작 후 작업자가 다시 수행, 멱등 키로 중복 방지 |
| 같은 아웃박스 작업을 작업자 둘이 동시에 꺼냄 | 같은 외부 호출이 두 번 나감 | 작업을 꺼낼 때 잠금으로 한 작업자만 가져가게 함 |
| 몰 인증 토큰 만료 | 모든 요청 실패 | 만료 응답 감지 시 재발급 후 한 번만 재시도 |
| 변환표에 없는 상태값 | 잘못된 정책 판단 | "알수없음" 처리, 경고 로그, 상담원 이관 |
| 몰 B가 200과 함께 실패 응답 | 실패를 성공으로 오인 | 어댑터가 본문 성공 여부를 검사해 공통 오류로 변환 |
| 몰 하나가 계속 느려짐 | 작업자가 그 몰에 묶여 다른 몰 처리도 밀림 | 몰별 동시 처리 한도와 시간 초과 분리, 지표로 감지 |

모든 시나리오는 테스트 하나씩과 짝을 이룬다 (11절).

## 11. 테스트 전략

정책표의 칸 하나와 장애 시나리오 하나가 각각 테스트 하나가 된다. 모든 테스트는 PR마다 CI에서 자동으로 돈다.

| 층위 | 대상 | 방법 | 개수 기준 |
| --- | --- | --- | --- |
| 단위 | 정책 계층 | 배송 상태 × 요청 유형 조합별 기대 결과 검사 | 정책표 칸 수만큼 (12개) |
| 단위 | 어댑터 변환 | 몰 응답 견본 → 공통 모델 변환 검사, 모르는 상태값 포함 | 몰당 상태값 수 + 예외 |
| 통합 | 어댑터 ↔ 가짜 몰 | 가짜 몰을 실제로 띄워 호출 | 공통 동작 × 몰 수 |
| 장애 주입 | 전체 흐름 | 지연·500 오류·중복 요청·토큰 만료·작업자 중단을 강제로 발생 | 9절 시나리오 수만큼 |
| 계약 | 공통 인터페이스 | 모든 어댑터가 같은 테스트 묶음을 통과하는지 | 새 어댑터 추가 시 그대로 재사용 |
| 부하 | 연동 계층 + 가짜 몰 | 몰 지연을 설정한 채 동시 요청을 늘려가며 처리량·응답 시간 측정 (CI 제외, 수동 실행) | 개선 전후 각 1회, 수치는 문서로 |

- 계약 테스트가 핵심이다. 몰 C를 추가할 때 이 묶음만 통과하면 된다는 게 "연동 추가 비용이 낮다"는 주장의 증거가 된다.
- 에이전트(모델 호출) 부분은 응답이 매번 달라 자동 테스트 대상에서 뺀다. 대신 도구 호출 이후의 백엔드 동작만 테스트한다.
