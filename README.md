# 주문 처리 연동 계층

서로 다른 방식의 API를 가진 쇼핑몰 2개를 하나의 취소·반품 인터페이스로 묶고, AI 상담 에이전트가 이를 안전하게 호출하게 만드는 파이썬 백엔드입니다.

> 진행 중인 프로젝트입니다. 설계 결정은 `docs/결정기록/`에 쌓입니다.

## 왜 만드나

에이전트가 실제 업무(취소·반품)를 처리하게 만들 때 어려운 건 모델이 아니라, 제각각인 외부 시스템을 믿을 수 있게 다루는 일입니다. 이 저장소는 그 문제를 축소 재현합니다.

- 몰마다 다른 인증·상태 코드·오류 형식을 **어댑터**에서만 흡수
- 같은 요청이 여러 번 와도 한 번만 처리되는 **멱등성**
- 우리 DB 저장과 외부 호출의 불일치를 막는 **아웃박스**
- 결과를 모를 땐 추측하지 않고 **재조회**, 그래도 모르면 상담원 이관

## 구조

```
src/
  claim_gateway/
    domain/        공통 주문·클레임 모델 (몰을 모름)
    policy/        취소·반품 가능 여부 판단
    integration/   공통 인터페이스, 아웃박스 작업자
      adapters/    몰별 어댑터
    api/           주문 처리 API
    agent/         에이전트 도구 호출 연결
  mock_malls/
    mall_a/        가짜 몰 A
    mall_b/        가짜 몰 B (일부러 A와 다르게)
docs/
  결정기록/        판단 지점별 결정과 근거
  트러블슈팅/      실제로 막혔던 문제와 원인 추적
  성능측정/        부하 테스트 조건과 결과
  몰명세/          몰 A·B API 명세
```

## 실행

```bash
# 전체 실행 (DB + 가짜 몰 2개 + 연동 서버)
docker compose up --build

# 로컬 개발
uv sync
uv run uvicorn claim_gateway.main:app --reload
uv run pytest
uv run ruff check . && uv run ruff format --check .
```

## AI 도구와 협업한 방식

설계 판단은 직접 하고, 구현은 AI 코딩 도구와 협업했습니다. 모든 AI 작성 코드는 PR로 들어오며, 줄 단위로 설명할 수 있을 때만 병합했습니다. 작업 규칙은 `CLAUDE.md`, `CONTRIBUTING.md`에 있습니다.
